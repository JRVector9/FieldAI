# I06 기존 연결 예약의 알림 경로 전환 설계 — 2026-09-25

## 범위와 불변식

AP·Field 연결 해제 뒤 **기존 Field 예약 하나씩** AP 세대 1에서 Field 세대 2로 명시 전환한다. 연결 전체의 세대를 일괄 변경하지 않는다. 기존 AP 문의 원본, Field 예약/고객 확인키, 이전 사건 및 두 제품의 구독을 유지한다. 실제 문자·카카오 공급사가 없으면 Field 고객 알림은 `blocked_integration`으로 기록하며 전송 성공으로 표시하지 않는다.

## 전환 순서

1. Field 예약 확인키를 가진 고객이 Field 화면에서 해당 예약의 향후 처리 알림을 Field가 담당한다는 고지를 보고 동의한다. 전화번호만으로 동의하거나 예약을 열 수 없다. Field는 동의 버전·시각·예약을 보존하고 확인키 원문은 보존하지 않는다. 동의는 연결 해제 전에는 받지 않는다.
2. Field owner가 기존 AP 사건/고객 알림 상태를 조회한다. AP가 404/장애이거나 어떤 사건이 미처리·발송 미상·공급사 전송 중이면 전환하지 않는다. 연결 해제 양쪽 ACK, 고객 접근/동의, 예약 revision을 요구한다. 이미 발생한 사건을 Field에서 다시 발송하지 않는다.
3. Field 서버가 연결별 HMAC으로 예약·ActionRequest·마지막 사건 ID/revision·전환 ID를 AP 공개 API에 보낸다. AP는 자기 연결이 revoked인지, 사건이 전부 연속·일치하는지, 기존 고객 알림 원장이 `not_applicable` 또는 공급사 미연결 `blocked_integration`인지 검증한다. AP는 이 예약의 세대 1 경로 종료를 자체 DB에 내구 기록하고 동일 전환 ID 재시도에 같은 영수증을 준다. 새로운 Field 전송 성공을 주장하지 않는다.
4. Field는 AP 호출 전에 전환 ID·고객 동의 ID·대조 기준 사건/revision을 자기 DB에 기록한다. 기준은 AP에 전달 ACK된 세대 1 사건의 연속된 마지막 지점이다. 연결 해제 뒤 생성돼 AP에 미전달된 사건을 대조 완료로 가장하지 않는다. AP 응답 분실·Field 서버 재시작·사업자 화면 새로고침 뒤에는 저장된 ID와 기준으로 같은 종료 영수증을 재시도한다.
5. Field는 받은 영수증과 현재 동의·예약 사건을 다시 검사한다. AP 기준 뒤에 생긴 모든 사건은 고객 직접 연락 `reached` 기록이 있어야 세대 2를 활성화한다. 단순 시도 `attempted`는 부족하다. AP 종료 뒤 Field 활성화 전에는 새 사건을 AP에 보내거나 Field 고객 자동 알림으로 만들지 않고 직접 연락 대상으로 보존한다. 고객 철회 중 활성화는 거부하고, 재동의 후에도 기존 전환 ID를 재사용한다.
6. 활성화 뒤 새 Field 예약 사건만 Field 알림 원장에 1회 기록한다. 이전 세대 사건은 재발송하지 않는다. AP event worker는 새 세대 사건을 전달하지 않는다. 실 공급사 연결 때에는 AP의 세대 1 알림 발송기가 발송 직전에 Field의 현재 경로/세대와 AP 자체 종료 원장을 재확인해야 한다. Field 상태를 확인할 수 없으면 보류한다. AP native 문의 알림은 Field가 없어도 계속 동작한다.

## 실패와 보존

- AP 또는 Field 장애: transfer는 대기/재시도 또는 명시 거부이며 자동으로 소유권을 전환하지 않는다. 기존 예약/확인키와 직접 연락 기록을 유지한다.
- 고객 확인키 미발급, 동의 없음, 타 예약/조직, 타 연결, 해제 미완료, 사건 누락/역순, supplier `unknown`/`sending`: 전환 거부. 사업자 화면에 이유를 보인다.
- 응답 분실/중복 클릭: Field DB에 저장된 전환 ID로 멱등 영수증을 복구한다. 아직 종료되지 않은 같은 예약에 새 브라우저가 다른 ID를 보내도 기존 ID를 사용한다. 이미 활성화된 경로에 다른 ID를 보내면 충돌한다.
- 기준 뒤 사건: 예약 revision이 바뀌어도 저장된 AP 종료 기준을 확장하지 않는다. 사건별 고객 도달을 기록한 뒤 활성화한다. AP inbox에 기준을 넘는 사건이 있으면 AP 종료를 거부해 대조 없이 숨기지 않는다.
- AP 202 수신과 해제의 경쟁: 연결 row lock으로 수신 commit과 해제 순서를 고정한다. 먼저 202를 준 inbox 사건은 해제 뒤에도 AP 내부 사건·알림 원장으로 처리해 종료 대조를 진행한다. 해제가 먼저 commit되면 새 사건을 거부한다. 종료 영수증 뒤 남은 inbox 사건은 `route_closed`로 거부하고 새 알림을 만들지 않는다. 실제 공급사 발송은 별도의 현재 경로 재확인이 필요하다.
- 고객 동의 철회: 향후 Field 자동 발송을 정지하고 직접 연락 경로를 표시한다. AP 경로를 자동 복구하지 않는다.
- 실제 provider 상태, 법적 보존 기간, 운영 키 회전·공급사/서버 장애 검수는 별도 게이트다. 이 설계의 mock 검사는 출시 승인이 아니다.

## 제품 경계와 검수

Field는 자신의 예약/고객 capability·route/알림 원장을 소유한다. AP는 자신의 연결/기존 사건·고객 알림 원장과 종료 영수증만 소유한다. 상대 제품 DB/module import는 없다. 공개 계약→AP 제공자 DB 검사→Field 소비자 DB 검사→실제 별도 HTTP/worker·320px 고객/사업자 화면→양쪽 장애·재시도 검수 순서로 진행한다. QA148~153, G-I1/G-I3 및 TASKS I05/I06이 적용된다.

## 현재 구현과 남은 경계

Field 고객 확인키의 동의/철회·사업자 전환, AP의 서명 종료 영수증, 예약 사건별 담당 제품/세대와 AP 전달 제외가 로컬 mock에서 구현됐다. Field 시작·AP 시작 해제의 별도 API/worker HTTP와 320px 고객/사업자 화면을 각각 검사했다. 이전 AP 사건은 다시 Field 알림으로 만들지 않고 전환 이후 새 Field 사건의 고객 원장은 `blocked_integration`이다. Field DB는 전환 ID/기준점/동의를 AP 호출 전에 저장하며 AP와 Field API를 실제 중단·재시작한 뒤에도 같은 ID를 복구했다. 해제 전후 대조 기준을 넘는 사건은 직접 연락 도달 기록 뒤에만 활성화하는 DB 검사를 통과했다. AP는 202를 준 뒤 해제된 inbox 사건의 내부 처리와 해제와 경쟁한 새 요청의 401 거부를 DB에서 검사했다.

실제 공급사 `unknown` 조회 및 AP 발송 직전 Field route 확인, 운영 키 회전·서버 장애/복구와 구독 종료·삭제 보존은 미구현이다. 따라서 최종 QA/G-I3와 운영 알림 발송 승인은 남아 있다.
